# 后端形态：Next.js 全栈路由 + Supabase（认证与数据），放弃纯静态导出

v1/v2 的"纯静态导出、零后端、全部计算在浏览器"服务于自主练习工具。v3 起产品方向转向教学管理平台：教师编辑题库、个性化安排学生测试、学情采集统计——全部是服务端密集型能力（写权限校验、跨用户聚合）。本 ADR 决策：移除静态导出配置，Next.js 走全栈形态（Route Handlers 承担后端 API），认证与数据由 Supabase 云服务支撑。**判题内核仍在浏览器执行**（sql.js/Web Worker 的性能与零边际成本优势不变），后端只承担认证、数据 CRUD 与未来的统计聚合。

登录走统一后端路由：前端提交（学号或邮箱 + 密码 + 阿里云行为验证码票据），后端核验票据、以服务端身份解析学号→邮箱映射、调 Supabase 密码登录后返回会话——anon 通道查不到任何用户信息，防枚举与防泄漏集中一处。数据安全底线是 Supabase RLS；service_role 密钥仅存在于服务端。

## Considered Options

- **保持纯静态 + Supabase Edge Function + RLS-only**：题库编辑权限、作业分配、学情聚合全部写进 RLS 策略（PL/pgSQL），业务逻辑埋进数据库策略难调试难测试；跨用户学情聚合在 anon+RLS 模式下要么视图要么全量拉到前端，均不可行。且阿里验证码核验已需 Edge Function，会造成"Edge Function + 未来还得再加后端"的两套后端形态，被否决。
- **保持题库编译期打包、仅认证上云**：部署最简，但"教师可视化编辑题库"要求题库成为运行时数据，静态打包与之根本冲突，被否决。
- **独立后端服务（NestJS/Express 单独部署）**：职责清晰但引入第二个部署单元与跨域配置；本项目本就是 Next.js，去掉一行导出配置即得同平台全栈能力，被否决。

## Consequences

- 失去"无环境变量、纯静态"的极简部署：Vercel 需配置 Supabase 与阿里云密钥，本地开发需 env 文件。
- E2E 测试从"天然离线"变为需 mock 外部服务（Supabase、阿里云、自有 /api 路由），测试基建有一次性的适配成本。
- 业务逻辑全部落 TypeScript（Route Handler → 服务模块），服务端代码需要与前端同级的测试纪律；RLS 仅作兜底防线而非业务规则载体。
