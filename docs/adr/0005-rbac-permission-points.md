# 权限模型：RBAC 权限点驱动，角色不进代码

学生、助教、教师的权限存在交叉（助教往往也是学生），且未来会新增角色。若代码中判定 `role === '教师'`，每次新增角色或调整职责都要改代码、发版。本 ADR 决策采用经典 RBAC 三段结构：**用户—角色—权限点**均为多对多关系；角色只是职责标签，不含行为规则；一切行为判定（前端显隐、后端放行、答案解锁豁免）只检查权限点（如「随时查看参考答案」），不检查角色。新增角色、调整某角色的能力，都是数据变更。

第一版仅投入使用权限点「随时查看参考答案」（挂载给助教、教师）；「编辑题库」「安排练习」「查看学情」三个权限点随表预定义占位但不挂角色，待对应功能实现时启用——权限点是数据，预定义零成本；代码仍遵循 YAGNI，不预实现任何未启用权限点的功能。

权限的真实验证分两层：前端判定只服务于界面显隐（体验层），后端路由与 Supabase RLS 是安全边界（见 ADR-0004）。

## Considered Options

- **硬编码角色枚举判定**：实现最快，但每次角色调整都是代码变更；权限交叉需写组合特判，膨胀后不可维护，被否决（也是本需求的原始动机）。
- **只建角色表、不建权限点表**：比硬编码好（角色可插），但"助教也能做题"这类交叉仍需在代码里写角色集合，角色词汇泄漏进代码，被否决。
- **ABAC（基于属性的判定）**：表达力最强，但教学场景的角色数量与规则复杂度远不需要属性引擎，过重，被否决。

## Consequences

- 权限点的命名成为长期词汇表：新功能设计时先命名权限点再写代码，措辞应与 GLOSSARY 的领域语言一致。
- 权限点集合需要纪律管理：占位不挂角色的权限点必须与真实规划的功能对应，防止占位膨胀。
- 角色分配与白名单配置第一版无管理界面（直接在数据库层操作），管理 UI 留待后续版本作为权限点启用。
